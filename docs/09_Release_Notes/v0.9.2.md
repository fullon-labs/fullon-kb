# v0.9.2 目标版本与升级说明

本文档站的节点、CLI 与 RPC 统一以 **FullOn Core v0.9.2** 为目标。发布标签对应 `2188e4f94a1e9fe564a31c33e497b464556f3650`，官方注解标签对象为 `6688825a23c4fe580acea00b38299a1518131232`；已与 GitHub 标签元数据交叉核对。源码审阅日期：2026-11-02。

## 适用范围

- [完整 RPC](../03_Operators/funod-rpc.md)、[交易历史](../03_Operators/transaction-history-rpc.md)已重新审阅路径、请求/响应和可用条件。
- [节点](../10_Developer_Guides/nodes.md)、[P2P](../10_Developer_Guides/p2p.md)、账户/ABI/code/合约调用等 CLI 示例已对照该提交；CLI 参数与旧基线的相关代码没有变化，但出处已固定到发布提交。
- [Docker Compose](../10_Developer_Guides/docker-compose.md)保留独立的模板提交，显式覆盖节点/tools 为 v0.9.2，不把模板默认值或 CDT 版本改写成虚假的同一版本。
- 合约、系统权限、RWID、CDT 和钱包各有独立版本。Core 升级不能证明这些组件的部署或兼容性；原有核验边界继续有效。

## 与旧版 RPC 文档的实质变化

| 项目 | v0.9.2 目标说明 |
| --- | --- |
| History 诊断 | 新增已注册的 get_optimization_suggestions、get_cache_analysis、get_maintenance_needs，双前缀均可用；trigger_auto_optimize 仍未注册 |
| History 响应 | 增加 history_status 及交易 account_index_complete；缺失的旧字段不能当作完整性保证 |
| History 恢复 | 过滤、预算、响应大小及持久缺口都影响查询；有缺口的数据库不因重启自动清空重建 |
| 构建与角色 | core/history 两构建；BP/RPC/seed 为运行角色；不能用配置开启未编译插件 |
| 管理 API | 默认拒绝非回环/非 Unix 管理监听器，签名入口始终 Unix-only |
| 本地恢复 | state/blocks 操作锁与 restore.pending 防止节点和物理恢复同时操作；先诊断，不删除锁/标记来绕过检查 |
| 覆盖上限 | 全可选功能构建最多 76 个逻辑操作、86 条路径；灰名单另加 3。不是默认发布包或在线节点的接口承诺 |

- Ubuntu 22.04 amd64 的 node/tools/组合 deb 包，以及 Linux x86_64 / macOS arm64 的便携归档与校验清单。

标签有 `v`，归档和 deb 文件版本部分通常没有 `v`。不要从名称推断所有平台、Docker 镜像或 CDT 镜像均存在。

## 升级与验收

1. 确认目标网络允许的版本、chain ID、协议特性与数据格式，保存旧包、配置及一致的数据备份。
2. 选择匹配角色、平台的发布包/镜像并核对官方校验和或摘要；拉取镜像不会替换旧容器。
3. 停止原进程后，按网络发布要求选择兼容快照或 replay。不要假定旧二进制能回读新状态，也不要删除恢复标记试错。
4. 核验实际运行版本，而不是只查看镜像标签或下载文件名：

```bash
funod --full-version
fucli version full
fuwal --full-version
```

5. 再核对 RPC get_info 的版本和 chain ID、head/LIB 推进、get_supported_apis、角色所需插件以及历史索引健康。BP 还需检查排班和签名服务。

本次只进行源码/发布元数据和文档验证，没有启动、升级或修改任何主网/测试网节点，没有执行链上写交易。历史 2026-09-03 的线上 RPC 观察仍保留原日期，不是本次部署证据。
